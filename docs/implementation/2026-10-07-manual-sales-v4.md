# Approved manual sales v4 implementation

Baseline e30a08e9559c37d9137701f0acdcc54e09b7c4de. User approved implementation and NET then SITE deployment.

## Binding requirements
- Customer profile edits affect current order contact/list/search by same-store customer_id; archived/unlinked orders remain visible. Current null fields stay null; historical order/address snapshots never rewritten by profile save. Search current AND historic normalized contact fields.
- Keep /orders/quick-links; rename everywhere Manuel satış. Remove duplicate manual drafts menu/creation UI, redirect list/new addresses. Preserve historical records/operations. Live order_drafts table currently empty.
- Social modal single platform instagram/facebook/x/pinterest/tiktok/whatsapp/other + optional socialReference. salesChannel manual/social. New sales default manual. Technical source in_store and POS numbering stay.
- fulfillmentMethod pickup/shipping defaults pickup. Shipping requires CRM customer name/phone + shippingAddress; email optional; shippingCents default0; billingAddress defaults delivery, optional separate. Shipping starts pending, pickup delivered. Existing guarded shipment/status/address flow handles shipping without financial/stock mutations.
- paymentParts [{partId UUID,paymentMethod cash/card/bank_transfer,amountCents integer>0}]. Repeated methods allowed, empty for zero credit. Sum <= total; initialCollectionCents derived. Existing credit customer/permissions/due-date rules apply when sum < total. Shipping fee excluded from discount base.
- Prepare freezes products/pricing/customer/delivery/parts; store prepareOperationId. Independently confirm each part after physical receipt using stable partId and Idempotency-Key. Each confirmation atomically posts receipt+collection event+account movement/balance immediately. On final complete allocate those SAME events to one receivable, never move cash twice. One order/stock deduction only.
- cash600 received/card400 fails: durable pending receipt and reservation, can park verified pending sale/new cart, reopen only remaining part. Unknown commits never cleared/switched. Dedicated revisePendingPayments only changes unreceived parts (can explicitly reduce to received total/attach customer and debt after credit permission validation), frozen price/channel/delivery unchanged.
- Manager-only returnPendingPart after actual full-part refund: append refund+negative account movement and immutable original receipt link. Mark abort intent before returning, prevent finalize race; cancel/release only after all net receipts0. No stock increment before completion. Pending-part events protected from generic accounting reversal/refund. Completed orders use current financial return/refund flow.
- Keep statuses: payment_pending until all planned parts received; payment_received thereafter; zero-credit directly completes. Receipt physical times/actors preserved across later completion/period boundary.
- V4 header X-Celebix-In-Store-Version:4. Preserve v1-v3 exact response/replay and block older mutators touching v4. Orders reader V2 header X-Celebix-Orders-Version:2 includes customerId/currentCustomer, salesChannel/socialPlatform/socialReference and fulfillmentMethod/billingAddress; V1 unchanged.
- Accounting channel WEB/POS remains; manual/social separate filter dimension. Pending collections visible in POS totals even before allocation; collection reporting not repeated at completion.
- Native shipping never writes stock. Keep narrow shipping exceptions to in_store_order_guard; never bypass financial/inventory protections. Financial return/restock remains one guarded operation after goods return, shipment status alone never restocks.
- Each mutator checks authority, same-store resources, expectedVersion and operation fingerprint; duplicate part is unique. Other part's version change must not cause repeat physical payment; replays checked before stale version.
